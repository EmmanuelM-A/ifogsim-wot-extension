# Analytical Support Document for Simulation Results

## 1. Introduction

### 1.1 Purpose of the Document

The purpose of this document is to provide guidance on understanding and interpreting the simulation results produced by 
program, particularly iFogSim core results. The document will help you to analyse these outputs, and gain a better 
insight into the performance of your IoT applications and make more informed decisions to optimize your system 
architecture, resource allocation, configurations and overall efficiency. 

### 1.2 Scope

This document focuses exclusively on the default simulation results generated by iFogSim, excluding any custom 
performance metrics. These results provide insights into the performance and efficiency of IoT applications. The key 
metrics analyzed in this document include:

- **Execution Time** – Total duration required to complete the simulation.
- **Application Loop Delays** – Time taken for data to travel through the IoT system.
- **Tuple Execution Delays** – Processing time of individual data tuples at different system nodes.
- **Energy Consumption per Device** – Power usage of each simulated device.
- **Total Network Usage** – Data transmitted across the network during simulation.
- **Cloud Execution Cost** – Estimated cost of cloud resource usage during execution.

Each of these metrics will be explored in detail in later sections, providing guidance on how to interpret them and how 
they impact IoT system performance.

## 2. Overview of Simulation Results

### 2.1 Types of Results

The simulation results are produced and calculated by iFogSim's simulation mechanism and is based on the constructed
application's topology and device and connection configurations. The system's topology follows this hierarchical
structure:

CLOUD <---> EDGE NODES <----> Virtual Devices (Sensors and Actuators)

The key performance indicators (KPIs) extracted from the simulation results include execution time, network delays, 
energy consumption, and cloud usage.

Additionally, the simulation tracks two types of Application Loops (AppLoops):

- **Regular App Loops** – Measure the standard data flow across the system. Below is an example of what a regular app loop
looks like:

```
AppLoop [SOURCE, M PROCESSING MODULES, DESTINATION] ---> N ms`

AppLoop [SmartDoorLock-0_SENSOR, MasterModule, lockState, WorkerModule-1, lockDoor, MasterModule, SmartDoorLock-0_ACTUATOR] ---> 21.485 ms
```

- **Event-Triggered App Loops** – Specifically track the response time of workflows initiated by Web of Things (WoT) event 
nodes. These measure delays from event initiation to final destination. Event AppLoops can be identified by the 
presence of the processing module `EventProcessor` in an app loop as shown below:

```
AppLoop [SOURCE, EventProcessor, DESTINATION] ---> K ms

AppLoop [snapshotTaken, EventProcessor, SmartCamera-0_ACTUATOR] ---> 19.782 ms
```

### 2.2 Key Metrics for Optimization

When optimizing IoT applications, the following key metrics should be carefully analyzed to enhance performance, 
scalability, and cost-efficiency:

- Application Loops (AppLoops) – Measures the time taken for data to travel from source devices (e.g., sensors), 
through processing nodes, and back to actuators or end-user devices. This is crucial for assessing the responsiveness 
of time-sensitive IoT applications.

- Tuple Execution Delays – Represents the time required to process individual data tuples at different fog devices or 
cloud nodes. This helps identify processing bottlenecks and can be analyzed per device or application module.

- Total Network Usage – Quantifies the data transmitted across the network during the simulation. Monitoring network
usage helps optimize communication efficiency and reduce unnecessary data flow.

- Cloud Execution Cost – Represents the estimated financial cost of using cloud resources, including processing, 
storage, and data transmission. Understanding this metric helps in optimizing cloud-based deployments for 
cost-effective operation.

## 3. Interpreting Simulation Data

### 3.1 Understanding the Metrics

Each metric provides insight into different aspects of IoT system performance. Here’s how to interpret them:

- **Execution Time** – If execution time is too high, it could indicate inefficient system design, excessive delays in
  processing, or an overloaded infrastructure. Reducing processing complexity or balancing workload distribution can help.

- **Application Loop Delays** – High values indicate network congestion or excessive processing latency. Optimizing the
  number of intermediate nodes and data paths can improve responsiveness.

- **Tuple Execution Delays** – High tuple delays suggest processing bottlenecks. Identifying which nodes experience
  excessive delays can help redistribute workloads efficiently.

- **Energy Consumption per Device** – High power usage on specific devices might indicate overuse or inefficient task
  allocation. Optimizing task scheduling and reducing redundant computations can lower energy consumption. Adjusting
  device configurations can also impact energy consumption.

- **Total Network Usage** – High network usage suggests excessive data transfers. Compressing data, using more efficient
  protocols, minimizing unnecessary transmissions can help or adjust the application topology mechanism.

- **Cloud Execution Cost** – A high-cost might indicate excessive reliance on cloud computing. Moving some processing to
  edge nodes can help reduce expenses like altering app module connections to the cloud.

## 4. Optimization Strategies

### 4.1 Reducing Execution Time

- Minimize redundant computations and optimize processing logic.
- Improve resource allocation by balancing workloads across fog and cloud layers.
- Reduce application loop size where possible.
- Changing application model design to minimize redundant processes or offload tasks to more efficient nodes.

### 4.2 Enhancing Network Efficiency

- Use efficient data transmission methods to reduce total network usage.
- Avoid unnecessary data replication between devices.
- Optimize the placement of processing nodes to minimize data hops.
- Reconfiguring network topology, Virtual Devices (VDs), or adjusting communication protocols.

### 4.3 Managing Energy Consumption

- Implement energy-aware scheduling policies.
- Modifying VD configurations, workload distribution, or task scheduling.

### 4.4 Optimizing Cloud Execution Costs

- Minimize dependency on cloud processing by leveraging edge/fog nodes.
- Use cloud resources efficiently by executing only high-priority tasks remotely.
- Altering application model design to shift processing loads to local fog nodes instead of cloud execution.

## 5. Troubleshooting and Common Issues

### 5.1 Identifying Bottlenecks

- If execution time is too high, check if specific nodes are overburdened.
- High tuple execution delays? Consider optimizing data flow and processing distribution.

### 5.2 Debugging Network Congestion

- Identify high-traffic network paths and optimize routing configurations.
- Consider using data aggregation techniques to reduce overall network load.

### 5.3 Resolving High Cloud Costs

- If cloud execution cost is excessive, review which tasks rely on cloud processing and offload where possible. Review
the `Simulation` class and its components for a better understanding.
